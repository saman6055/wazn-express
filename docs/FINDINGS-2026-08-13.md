## Fixed

### The batch package count was wrong in both directions
`batches.totalPackages` is incremented when a package is assigned and is
never decremented, never recomputed, and not written at all by some of the
paths that assign one. Every batch in your list showed `0` while holding
parcels.

Not only cosmetic: the delete button is offered only for an empty batch, and
every batch looked empty, so it appeared on batches full of parcels. The
server counts the referencing rows itself and refused them, so nothing was
ever lost — but the screen was lying both ways at once. The list now counts
the parcels in one grouped query per page.

### The portal's hottest query had no index
Every portal page load asks for "this customer's parcels in these batches",
seven times on one screen. MySQL uses one index per table, so the
single-column `customerId` index was chosen and the customer's entire parcel
history read and then mostly discarded. Added a composite index on
`(customerId, batchId)`.

### Dark mode washed out surfaces and text
214 surfaces, 1511 text colours and 11 borders across 158 files had no
dark-mode counterpart. Reported on two screens, present across the app. The
change is provably additive — strip every `dark:` class and the files are
identical to what they replaced, so light mode cannot have moved.

### Permissions had drifted from the app
Thirteen sidebar pages had no permission entry at all, and `canViewPath`
ends with "if nothing is mapped, show it" — so every one of them was visible
to every staff member regardless of their permissions. Two more permissions
pointed at paths renamed months earlier, so they governed nothing while
still appearing to work in the admin UI, which is the worse failure.

### Scanner screens showed raw keys
69 `scan.*` translation keys existed in no locale file. Staff saw
`scan.selectBatch` where the label should be, in all four languages.

## Open — your call

### Two rate limiters are defined and never mounted
`mutationLimiter` and `fileUploadLimiter` are exported from
`server/middleware/rateLimiter.ts` and mounted nowhere. The only protection
in force is the global 1000 requests/minute per IP plus the auth limiter on
login. This is already written up in `RATE_LIMIT_REPORT.md`.

**Why I did not just wire them up:** it changes how production traffic is
throttled. `mutationLimiter` allows 200 mutations/minute per IP; batch
assignment fires one mutation per scan, and a bulk register fires many. Get
it wrong and a warehouse operator is cut off mid-batch. It wants a number
chosen with knowledge of how fast your staff actually work.

There is now a test recording which limiters are mounted, so the day they
are wired up is a deliberate edit rather than a drift.

### `store.createOrder` is unauthenticated by design
Anyone can place a storefront order without an account. The price is
recomputed server-side from the stored product, so the amount cannot be
driven from the request — that part is right. But with only the global
limiter in force, one IP can create roughly a thousand fake orders a minute.
Worth a captcha or a per-phone throttle before the shop is promoted.

### `deletionLogs` has two different shapes
The `CREATE TABLE` in `server/_core/migrations.ts` and the drizzle schema in
`drizzle/schema/admin.schema.ts` describe different tables — different
columns, not just different order. Whichever one is wrong, code written
against the other will fail at runtime. I avoided it entirely for the
recycle bin by adding a separate `deletedRecords` table rather than building
recovery on a table nobody can describe. Worth reconciling before anything
else uses it.

### Financial records should never enter the recycle bin
Invoices, payments and ledger entries are deliberately not in the bin. In
accounting you do not delete and restore a payment — you post a reversal. If
a paid invoice could be deleted and restored, a customer's balance could
change twice, silently. If you later want those recoverable, the right shape
is void/reverse, not delete/restore.
